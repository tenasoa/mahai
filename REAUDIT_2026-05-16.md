## 🔴 PROBLÈMES CRITIQUES — ÉTAT

### ✅ CRIT-1 : CSP Headers — **RÉSOLU**
- **Fichier :** `next.config.js`
- CSP complète avec `default-src`, `script-src`, `style-src`, `img-src`, `connect-src`, `frame-ancestors`, `base-uri`, `form-action`
- Headers X-Frame-Options, X-Content-Type-Options, Referrer-Policy dans `proxy.ts`
- ⚠️ **Limitation :** `'unsafe-eval'` et `'unsafe-inline'` encore présents dans `script-src`. Le plan d'action recommandait leur suppression avec approche nonce-based. Non fait.

### ❌ CRIT-2 : Validation DIRECT_URL — **NON RÉSOLU**
- **Fichier :** `lib/env.ts`
- `DIRECT_URL` n'est toujours pas dans le schéma Zod
- `lib/db.ts` utilise `process.env.DATABASE_URL || process.env.DIRECT_URL` sans validation
- **Risque :** Si `DATABASE_URL` est absent (ex: env de staging), l'app démarre avec un `DIRECT_URL` invalide et échoue au runtime au lieu de crasher au démarrage
- **Impact :** Faible en production (DATABASE_URL prioritaire), mais réel en environnement non-standard

### ⚠️ CRIT-3 : Admin Auth Bypass — **PARTIELLEMENT RÉSOLU**
- **Fichier :** `proxy.ts`
- ✅ Vérification du rôle ADMIN par requête SQL directe (contourne RLS Supabase)
- ✅ Redirection des non-ADMIN vers `/`
- ❌ **Fallback dangereux maintenu** (lignes 118-123) : si la DB est down, l'accès admin est **autorisé** avec le commentaire "la page vérifiera le rôle via ses propres server actions"
- **Recommandation initiale non suivie :** "Always deny on error"
- **Risque :** Une panne DB transitoire ouvre toutes les routes admin

### ✅ CRIT-4 : Validation paramètres Blog — **RÉSOLU (partiel structurel)**
- **Fichier :** `app/api/blog/posts/[slug]/route.ts`
- Utilisation de Supabase `.eq('slug', slug)` → paramétrage automatique, pas d'injection SQL
- Filtre `.eq('is_published', true)` qui empêche de lire les brouillons
- Pas de validation Zod des query params → possible 500 au lieu de 400 sur entrées invalides
- **Sévérité rétrogradée de CRITICAL à LOW** (l'injection SQL est structurellement impossible via le query builder Supabase)

## 🟠 PROBLÈMES HAUTS — ÉTAT

### ✅ HIGH-1 : Rate-Limiting API — **RÉSOLU**
- **Fichier :** `lib/rate-limit.ts`
- Implémentation Redis (Upstash) + fallback mémoire pour le dev local
- Scripts Lua atomiques (sliding window ZSET)
- Rate-limiters spécialisés : auth (5 req/15min), payment (10 req/heure)
- Fallback safe : autorise si Redis est down (ne bloque pas les utilisateurs)
- **Implémentation complète et robuste**

### ❌ HIGH-2 : Protection CSRF — **NON RÉSOLU**
- Aucune implémentation CSRF pour les routes API traditionnelles (`/api/*`)
- Next.js Server Actions ont une protection CSRF native (header `Next-Action`), mais les routes API REST n'en bénéficient pas
- **Routes exposées :** `/api/admin/*`, `/api/payment/webhook`, `/api/editor/upload-image`
- **Risque :** CSRF possible sur les routes sensibles si un attaquant peut faire exécuter des requêtes par un admin authentifié
- **Fix recommandé :** Token CSRF dans un cookie `SameSite=Strict` + header `X-CSRF-Token` vérifié dans un middleware

### ✅ HIGH-3 : Validation Upload Fichiers — **RÉSOLU**
- **Fichier :** `app/api/editor/upload-image/route.ts`
- ✅ Vérification d'authentification (401)
- ✅ Vérification de rôle (403) — whitelist `CONTRIBUTEUR | ADMIN | PROFESSEUR`
- ✅ Whitelist MIME types : JPG, PNG, WebP, GIF, SVG
- ✅ Limite de taille : 10 MB
- ✅ Stockage Vercel Blob (pas de stockage local)
- ✅ Auth aussi sur la méthode DELETE

### ⚠️ HIGH-4 : Monitoring Connexions DB — **PARTIELLEMENT RÉSOLU**
- **Fichier :** `lib/db.ts`
- Pool configuré (max 10, idleTimeout 30s, connectionTimeout 10s)
- Logging conditionnel (`LOG_DB_QUERIES=true`)
- Logger structuré avec `logger.dbError()`
- ❌ Pas de métriques de saturation du pool (connections actives/en attente)
- ❌ Pas d'alertes sur connexions bloquées ou timeouts
- **Recommandé :** Instrumenter le pool avec `pool.on('error', ...)` et exposer les métriques via Sentry ou un endpoint `/api/health`

## 🔵 NOUVEAUX PROBLÈMES IDENTIFIÉS

### LOW-1 : `any` excessif dans `lib/` (57 occurrences)
- Acceptable pour le code AI (TipTap AST, PDFKit types) — arbres de contenu dynamiques
- Problématique dans `lib/sql-queries.ts` : `getSubjects(filters: any)` et `params: any[]`
- **Recommandé :** Typer `filters` avec une interface explicite

### LOW-2 : Fallback `SUPABASE_SERVICE_ROLE_KEY` → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- **Fichier :** `app/profil/[userId]/page.tsx` (Server Component)
- Le fallback est du rôle admin vers le rôle anon → direction safe
- Mais l'intention est floue : pourquoi utiliser la service role key si la anon key suffit ?
- **Risque faible** (Server Component), mais à documenter

### LOW-3 : Pas de `SameSite=Strict` sur les cookies de session
- `proxy.ts` ne définit pas `SameSite` sur ses cookies
- Les cookies Supabase ont probablement leur propre config → à vérifier
- **Recommandé :** Forcer `SameSite=Strict` sur les cookies applicatifs

### LOW-4 : Pas de vérification `rowCount` après `UPDATE` atomique
- `app/api/blog/posts/[slug]/route.ts` : le `UPDATE views = views + 1` n'est pas atomique (2 requêtes séparées)
- **Risque :** Race condition sur le compteur de vues
- **Fix :** `UPDATE "BlogPost" SET views = views + 1 WHERE slug = $1`
